{# ---- S2 the problem --------------------------------------------------- #}

A WAF rule is somebody else’s idea of normal.

Rate limits are a number you guessed. Signature lists are a description of last year’s attacks. IP reputation is a judgement about a stranger made somewhere else. All three have the same defect: none of them has ever seen your site.

So the limit you set is either loose enough to miss a scraper that is quietly costing you money, or tight enough to throttle your own checkout on a Friday. A burst that is routine for a busy storefront is extraordinary for a documentation site, and no shared rule can know which one you are.

01 · Fixed rate limits

A number chosen before any traffic arrived. It is wrong the day your traffic changes shape, and nothing tells you.

02 · Signature lists

A description of attacks that have already been catalogued. Useful, and by construction always behind.

03 · IP reputation

Someone else’s opinion of an address, formed on someone else’s site. It says nothing about what that address did to you.

{# ---- S3 how it works -------------------------------------------------- #}

Three moving parts. Two of them are ours.

  1. 01 · The agent watches

    A thin Python client tails your nginx access log and batches request metadata, never bodies and never payloads. It ships with no ML and no AWS SDK.

  2. 02 · The backend measures

    We aggregate to one record per source IP per five-second bucket and score it against a per-tenant IsolationForest that was trained last night on your traffic and nobody else’s.

  3. 03 · The agent enforces

    Decisions come back in the same HTTP response. Your agent writes them into nginx or iptables, whichever it finds, and removes them itself when the timer runs out. Nothing else ever will.

{# ---- S4 sigma --------------------------------------------------------- #}

σ, in one screen.

σ (“sigma”) is one standard deviation: the natural unit of unusual for a given dataset. It is not a score we invented, and it does not mean the same thing for two sites. That is the entire point.

Nearly all ordinary activity sits inside 3σ of its own mean. We leave that alone. Between 4σ and 5σ we slow the source down for five minutes. Past 5σ we refuse it for an hour. Both timers expire on their own.

Why not just use the raw anomaly score?

Because we tried. The same brute-force attack scored −0.204, −0.105 and −0.092 against three successive models of the same tenant, crossing our fixed −0.1 threshold somewhere in the middle. A number that changes meaning every night cannot be a threshold, and it certainly cannot be shown to you.

{# ---- S6 what it doesn't do yet ---------------------------------------- #}

What it doesn’t do yet.

  • No external tenant has used it. It is deployed, the full loop has run end to end on production against our own demo tenant, and no one else has registered. You would be first.
  • No single sign-on. You sign in with an email and a password. There is no OAuth, no SAML and no SCIM, so there is no way to attach this to your company directory.
  • No edge rate limiting. We dropped API Gateway to stay inside the free tier, and we did not get that back.
  • Throttling is coarse. At 100% of the day’s free-tier share we refuse telemetry wholesale rather than shaping it per tenant.
  • We store end-user IP addresses. If that is a compliance problem for you, it is a compliance problem, and we have not solved it.

Questions

{#

What exactly leaves my server?

Counts, per IP, per five seconds: request count, error count, POST count, total bytes, total time, distinct URI count, distinct user-agent count. No URLs, no bodies, no headers, no cookies.

What happens if your backend is down?

Your agent keeps serving traffic and stops receiving decisions. Existing mitigations expire on their own schedule. Nothing fails closed.

Can it block my own monitoring?

Yes, and that is what the allowed list is for. An allowed IP is exempt from mitigation and excluded from training, so allowing one does not teach the model that its pattern is normal.

What if it blocks a real customer?

One click in the console lifts it immediately and permanently. We got this wrong for a while. The button reported success and left the block in place for up to an hour. It does not any more, and there is a test named after the failure.

Does an attacker train the model?

Buckets judged hostile are flagged and excluded from the next retrain. We found this by reproducing it: three copies of an attack in the training window and IsolationForest stops finding it unusual, because three identical points are a cluster and a cluster is not an outlier.

How is a bad model kept out of production?

A validation gate rejects models that would block too much normal traffic, or whose score spread has destabilised. The previous model stays.

Why standard deviations and not a score?

Because a raw anomaly score changes meaning every time the model is retrained. See σ, in one screen.

Is it really free?

Yes, with a stated cap. See the ceiling.
